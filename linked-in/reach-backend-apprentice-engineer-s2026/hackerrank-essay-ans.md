**Question 3**

The project I will be selecting is Git-Lint. This project is meaningful to me because I created it for myself as a tool to use. It is an automatic event-driven code reviewer, conditioned on GitHub webhooks for the opening of a pull request. It analyzes the code diffs in relation to embedded parts of a codebase, and from there, generates an analysis of changes and the effects it may have, as well as possible improvements. Here is the GitHub repository link: https://github.com/kylehton/Git-Lint
I created this project because during project creation and coding, I never really knew whether the code I was writing was good quality code or not. I didn't really have too much to base my deductions off of, and conventions online were all different. So, I decided to create a service that would do that for me. The project was aimed at creating a code review tutor to help me deduce the quality of my code as well as help me learn from any mistakes I made without knowing. I built this project end-to-end myself, using FastAPI as the instance framework, OpenAI as the LLM for code analysis, Pinecone for vector embedding snippets, and S3 for full codebase repository storage. The biggest challenge I faced was configuring the vector databases and creating the snippets for the vector embeddings in Pinecone. I delved straight into creating it alongside Claude, but ran into repeated problems where the embeddings were duplicates under different hashes, and some code segments, and even some files entirely, were not being embedded and stored properly. So, I took a step back and did more research on it myself, realizing that Claude had written in a faulty segment that was confounding multiple segments together. I fixed this issue myself, as well as the hash confusion. I am actually grateful for this, as it helped me gain a deeper, stronger understanding of vector databases. From there, I explored how I could prompt my AI coding assistant better, and discovered the CRISPE framework, which I still use to this day. This helped me navigate linking code segments with their vector embeddings between Pinecone and S3, and retrieving them for contextualization. Using Pinecone's vector search and embedding parts of the code diff as the input, I was able to contextualize my analysis prompts under my specific filters. The one practice I took away from this was how important comments were. After my first iteration of this, using OpenAI Chat Completions API then Responses API, OpenAI released their Agents SDK. After reading into it, I sounded cool to build with, so I decided to modify Git-Lint. Using the comments I had written, I was able to understand what parts of my function did what, and was able to put full effort and attention into learning how AI agents worked, and how agentic systems were built. I then built a pseudo-orchestration system using OpenAI's Agents SDK to fully manage the process, making it more solidified and structured. I delegated certain tasks to certain agents, one for analysis, one for summarization, and one as an overseeker, for orchestration. Then, I chose to deploy the service on AWS Lambda. I chose this for two reasons: that downtime was very probable, and that it was horizontally scalable. AWS Lambda can, in theory, scale horizontally infinitely, where it will run as many instances of functions as necessary. In my use case, it was really not needed, since I did not have the money to host this publicly for others to use my OpenAI API key. However, I wanted that option to be there in case I ever decided to. The biggest factor for my selection was the fact that AWS Lambda spins down the functions to a sleep state during non-usage. The inherent behavior of pull requests to main is that they are not done all the time, especially not by a single individual. So, having the application deployed and live the entire time would have been a waste of resources and unnecessary. I chose to have it spin up only in times of usage because it would be infrequent and occasional, and so I could prevent spending costs to keep it hosted for essentially no reason.
